# Phase 79 / Plan 01 — Q1 + Q2: Small-City Routing Correctness

**Goal:** clicking a *non-hub* regency marker (Tembilahan, Rengat, small kabupaten towns) must produce either a real corridor or an explicit, visible failure — never a silent no-op and never a whole-island Belawan → Bakauheni line.

**Scope:** `frontend/lib/mapboxRoutingService.ts`, `frontend/components/map/CrisisMap.tsx`, `frontend/components/dashboard/DashboardClient.tsx`, `backend/app/adapters/cpu_routing_adapter.py`.

## 2. Q1 decision constraint (non-negotiable)

**Always-show-all corridors.** The operator must be able to compare Darat / Laut / Udara side by side. Therefore:

- Do **not** filter corridor computation by `selectedModality`.
- Do **not** hide sea/air corridors just because the operator picked `truck`.
- Ambiguity is resolved by **provenance labels + visibility toggles** (Plan 03), not by suppressing geometry.

This constraint is why Plan 01 fixes routing *inputs* while Plan 03 fixes *legibility*.

## 3. Fix design (Q1 routing, Q2 coordinates)

### 3.1 `normalizeRegencyId` — strip the render index before matching

`frontend/lib/mapboxRoutingService.ts` (new export, ~line 405):

```ts
export function normalizeRegencyId(nodeId: string): string {
  return nodeId.replace(/^regency-\d+-/i, 'regency-');
}
```

Rules:

- The **original** ID stays the React key, Mapbox feature id, and `selectedOriginNode`/`selectedDestNode` value.
- Only the *lookup key* is normalized.
- Applied at every gazetteer comparison site: `CrisisMap.tsx` endpoint resolution (lines 1353, 1398) and `DashboardClient.resolveNodeInfo` (line ~758).

### 3.2 Require coordinates — no silent return

`DashboardClient.updateBaselineMapboxRoute` now returns `Promise<boolean>`:

1. If either endpoint has no coords → abort in-flight request, bump `routeCalculationReqIdRef`, clear `currentMapRoutes` + `selectedCrisis.route_recommendations`, null `routingInfo`, reset `activeRouteIdx`/`hiddenRouteIndices`, set `routingError = 'Rute tidak ditemukan untuk titik yang dipilih.'`, toast `error`, `return false`.
2. Callers (`handleNodeSelected`) only emit the success toast when `routesReady === true`; failures already surface through the banner/toast path.
3. Empty `routes` array from the router is treated as a failure, not a success.

### 3.3 Backend: explicit `no_route`

`backend/app/adapters/cpu_routing_adapter.py`:

- New `_build_no_route_response(...)` (line 538) returns `status: "no_route"`, `routes_count: 0`, `routes: []`, `snapped_origin_node: null`, `snapped_dest_node: null`, the unresolved ID, optional coords, a message naming the ID, and `compute_time_ms`.
- Origin branch (line 614) and destination branch (line 646) return it instead of snapping to first/last graph node.
- `NODE_ALIASES` resolution is preserved: aliases that *do* exist in the graph still resolve (e.g. `belawan` → `belawan_port`); only genuinely unknown IDs fail.

**Message contract (Indonesian, names the failing ID):**

> `Titik asal '<id>' tidak dikenali pada graph jaringan jalan dan origin_coords tidak tersedia. Fallback ke node graph pertama dinonaktifkan.`

**Deliberate behavior change:** the old first/last-node snap is deleted, not feature-flagged. A silent geography bug is worse than a visible refusal.

### 3.4 Modality: keep computing, stop pretending

Per the Q1 constraint, all corridors continue to be computed. What changes:

- The frontend no longer *claims* a modality-scoped result; `selectedModality` remains a fleet/visual filter.
- The sea corridor's implausibility is handled at the presentation layer (Plan 03: `sea` class, thinner island-ring stroke, explicit legend).
- `_modality` stays intentionally unused in `calculateAIDynamicDetourRoutes`; this is documented in Plan 06 as a pending decision, **not** silently “fixed” by filtering.

## 5. Risks / trade-offs

- **More visible errors.** Removing the silent return means operators will now see failures that previously “did nothing”. This is intended: silence was the bug.
- **`no_route` is currently unused by the frontend.** `api.routing.optimizeRouting` types `status` but `updateBaselineMapboxRoute` only reads `optimization_summary`; the banner therefore comes from missing coords / empty routes, not from `no_route`. Surfacing `no_route` explicitly is logged in Plan 06.
- **Render warm/cold split.** A correct small-city request can still take 30–50 s on a cold Render instance; that is Plan 02's problem, not a routing defect.
