# Phase 82 / Plan 01 — Truck Asset vs Travel/Rit Split, ERP Ledger, Two-Step Onboarding

**Goal:** separate the **truck asset** (registered once: nopol, VIN, BPJT golongan, driver, tenant) from the **travel/rit** (one row per trip: origin/destination, cargo, SLA, baseline vs actual cost), then derive every ERP rupiah from that ledger instead of from static percentages. The dispatcher onboarding flow becomes a two-step wizard: Step 1 saves the asset, Step 2 creates the rit against it using gazetteer-verified coordinates only.

## 2. Decision constraints (non-negotiable)

1. **Backward compatibility.** `custom_fleet_vehicles` is untouched. Legacy rows must remain readable as assets and must still be valid `truck_id` references for a new rit. Deletion of a legacy row stays on the old endpoint.
2. **Actual-recorded gate.** A rit with no realised outcome must report **Rp 0 savings**. It may show a baseline cost, but it must not claim a saving from an assumption.
3. **Split sums exactly.** `saved_fuel_cost_idr + saved_toll_idr + saved_spoilage_idr + saved_labor_idr == saved_cost_idr`, and `saved_cost_idr == baseline_cost_idr − actual_cost_idr` at rupiah precision. No hidden percentage, no residual bucket.
4. **No fabricated coordinates.** Origin/destination must come from a gazetteer hit with real `lat`/`lon`. A failed search produces a visible error — never a hub centroid and never `[0,0]`.
5. **Indonesian operator labels.** Every user-facing string is Indonesian; money uses `id-ID` grouping.
6. **Per-company scope.** Dispatchers read and write their tenant's assets/travels. Regulators see macro aggregates only. Guests see aggregates with zero writes.
7. **Single source of truth for cost constants.** BPJT tariffs, Pertamina rates, fuel consumption, driver overtime and spoilage deltas live in `spoilage_hedging_service` and are imported — never duplicated as literals in routers or UI.

### 3.2 `travel_ledger_service` — the ledger math

`_apply_ledger` (line 159) recomputes every field from raw inputs:

```
baseline_cost = fuel(baseline L × Pertamina rate)
              + BPJT toll(baseline_toll_segments, golongan)
              + spoilage(cargo_value × (1 − e^(−δ·blocked_delay)))
              + labor((baseline_time + blocked_delay) × Rp 50.000/jam)

actual_cost   = the same formula on realised time / fuel / toll segments.

saved_cost    = baseline_cost − actual_cost
                (split into fuel / toll / spoilage / labor, components rounded
                 first so the sum is exact)
efficiency %  = saved_cost ÷ baseline_cost × 100 (0.0 when baseline is 0)
```

Rules enforced in code:

- `cargo_value_idr` empty → `tonnage × 1000 × tier.default_price_per_kg`, recorded as `cargo_value_source = "tier_default_price"`.
- `baseline_distance_km` empty → haversine between the two gazetteer points, `distance_source = "haversine_gazetteer"`.
- `baseline_fuel_liters` empty → distance ÷ `TRUCK_FUEL_CONSUMPTION_KM_PER_LITER` (3.5 km/L).
- **No actuals → actuals mirror the blocked baseline**, so every savings component is 0 and `actual_recorded = FALSE`. This is the Rp 0 gate.
- Fuel rate = Pertamina base × `(1 + inflation_shock_factor)` via `get_effective_fuel_rate`; spoilage via `get_spoilage_loss`.
- `create_travel` (line 286) resolves the asset (master first, legacy second), snapshots `truck_name`/`company_id`/`driver_name`, inherits golongan/fuel type unless overridden, sets `sync_status = "pending"`, then applies the ledger.
- `update_travel` (line 309) applies only `exclude_unset` fields, flips `actual_recorded` when `actual_time_hours` arrives, recomputes, and stamps `delivered_at` on `status = delivered`.
- `solve_and_persist_hedging` (line 337) builds a `HedgingSolveRequest` from the rit (deriving detour distance/time from actual-vs-baseline when omitted), solves the cost matrix, and persists policy + net savings on the row.
- `build_erp_summary` (line 484) aggregates one scope: `DISPATCHER_DETAIL` (totals + per-company + per-rit rows) or `REGULATOR_AGGREGATE` (totals + per-company, `trips: []`).

## 6. Risks and trade-offs

- **Two stores.** The Supabase tables and the local SQLite tables are kept in lock-step by hand. The runtime path writes SQLite only; `sync_status` is set to `pending`, and no drain worker exists yet (see Phase 82 learnings 1.4). The migration is therefore provisioned-but-unpopulated, not a live remote read path.
- **Open read policies.** Migration 014 grants `SELECT` to `public` and write to any `authenticated` session (`USING (true)`). Tenant isolation is currently enforced by router/service filters, not by RLS predicates. This matches earlier pilot migrations but is not defence-in-depth.
- **Actuals without toll segments.** `_apply_ledger` treats `actual_toll_segments = None` with `actual_recorded = true` as "no toll used", which can credit the full baseline toll as a saving. The wizard does not expose actual toll segments. This is a real overstatement risk and is logged as a concern in the learnings document.
- **Legacy asset semantics.** A legacy row maps `organization_id` into both `company_id` and `company_name`; a legacy row with a free-text org name is matched through `matches_tenant`, not a stable claim.
- **Rounding contract.** Savings are derived from already-rounded rupiah components, so the split is exact by construction; floating-point tolerance is still used in tests (`abs=1`) to absorb JSON round-trips.
- **ERP freshness.** `ERPSavingsPanel` accepts a `refreshKey` prop but `ReportsSection` does not pass one, so the panel does not auto-refresh after an onboarding completion in another tab of the same session.
