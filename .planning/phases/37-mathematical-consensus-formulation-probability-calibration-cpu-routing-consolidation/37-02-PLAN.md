Create `data/road_network_sumatra.json`.
Construct a comprehensive, realistic graph of Sumatra arterial logistics corridors containing at least 50 junction nodes across:
1. **Strategic Seaports & Airports**: Pelabuhan Belawan, Pelabuhan Dumai, Pelabuhan Teluk Bayur, Pelabuhan Panjang, Pelabuhan Bakauheni, Bandara Kualanamu, Bandara Minangkabau, Bandara Sultan Mahmud Badaruddin II.
2. **Key Toll Expressways (Jalan Tol Trans Sumatera - JTTS)**:
   - Tol Belmera (Belawan-Medan-Tanjung Morawa)
   - Tol Medan-Kualanamu-Tebing Tinggi
   - Tol Tebing Tinggi-Indrapura
   - Tol Pekanbaru-Dumai
   - Tol Kayu Agung-Palembang-Betung
   - Tol Bakauheni-Terbanggi Besar
3. **National Arterial Highways (Jalan Lintas Sumatera - Jalinsum)**:
   - Lintas Timur (Jalintim): Medan - Tebing Tinggi - Kisaran - Rantauprapat - Duri - Pekanbaru - Jambi - Palembang - Bandar Lampung - Bakauheni
   - Lintas Tengah (Jalinteng): Tebing Tinggi - Pematangsiantar - Tarutung - Sibolga - Padang Sidempuan - Bukittinggi - Solok - Lahat - Baturaja
   - Lintas Barat (Jalinbar): Padang - Painan - Mukomuko - Bengkulu - Krui - Liwa
4. **Critical Mountain Passes & Vulnerable Bottlenecks**: Sitinjau Lauik (Padang-Solok), Bukit Barisan Tarutung-Sibolga, Curup-Lubuklinggau, Jembatan Way Sekampung.
Each node must have `id`, `name`, `province`, `lat`, `lon`, and `type`.
Each edge must have `from_node`, `to_node`, `distance_km`, `base_speed_kmh`, `corridor_name`, and `is_toll`.
Include bi-directional edge definitions.
</action>

<action>
1. Create `backend/app/adapters/cpu_routing_adapter.py`:
   - Initialize graph directly from `data/road_network_sumatra.json`.
   - `solve_shortest_path(origin_id, dest_id, hazard_zones=None, k_alternatives=3) -> dict`:
     - Uses NetworkX Dijkstra / $k$-shortest simple paths with dynamic hazard penalties (segments intersecting hazard radius $+ 2\text{ km}$ penalized $\times 10.0$ or 9999).
     - Calculates route polylines, total distance (km), ETA (minutes), fuel cost delta, and risk scores.
     - Execution time must be $< 30\text{ ms}$.
   - `solve_fleet_vrp(locations, cost_matrix, fleet_size=3, vehicle_capacity=120.0) -> dict`:
     - Solves Capacitated Vehicle Routing Problem (CVRP) using Google OR-Tools routing solver if available, with a fast greedy / 2-opt NetworkX fallback if OR-Tools is not installed.
     - Returns vehicle routes, stops per vehicle, total route cost, and travel time savings.
     - Execution time must be $< 150\text{ ms}$ for 50 nodes.
2. Refactor `backend/app/services/cuopt_tomtom_service.py`:
   - Replace calls to `CuOptAdapter` with `CPURoutingAdapter`.
   - Update solver metadata to honestly state: `"Deterministic CPU Solver (NetworkX + Google OR-Tools)"`.
   - Retain the exact API response contract so frontend callers (`/api/v1/routing/optimize-cuopt`) experience zero breaking changes.
3. Update `backend/app/routers/routing_router.py`:
   - Clarify endpoint docstrings reflecting honest CPU compute architecture.
</action>
<acceptance_criteria>
- `backend/app/adapters/cpu_routing_adapter.py` exists and implements `solve_shortest_path` and `solve_fleet_vrp`.
- A 50-node routing run executes in $< 150\text{ ms}$ on CPU.
- `backend/app/services/cuopt_tomtom_service.py` uses `CPURoutingAdapter` without errors.
- `POST /api/v1/routing/optimize-cuopt` returns HTTP 200 with solver status "success" and compute time < 150 ms.
</acceptance_criteria>
</task>
